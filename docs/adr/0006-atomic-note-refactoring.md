# Atomic Note Refactoring with Compensating Rollback

Because atomic transactions spanning both the Vault and the SQLite Index do not exist, we encapsulate the multi-note refactoring workflow in a dedicated application `RefactorService` that drives a LIFO compensating rollback stack. When a Note is renamed via `RefactorService.renameNote`, the service renames the target Note in the Vault, rewrites self-referential links, and refactors incoming Wiki-links across other referencing Notes discovered through the SQLite Index. Any disk I/O or SQLite error during this refactoring process automatically unrolls prior mutations via compensating actions to maintain consistency between Notes in the Vault and the SQLite Index without requiring filesystem locks or staging directories.
